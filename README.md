**מנגנון עתודה: **

רשימת ערכי ההחלטה של המשרד כוללת "התקבל ככשיר שני". על בסיס זה, אם המועמד הנבחר לא מתקבל בפועל או פורש, המערכת קוראת אוטומטית למועמד הבא בדירוג העתודה, בלי להתחיל את התהליך מחדש.

**ארכיטקטורה טכנית**

**שכבות המערכת**

**תצוגה (React + TypeScript)  **מסכי משרה, מפ"ל וסטטוס; מסכי מועמדים, ניקוד ושקלול; מסכי הרשאות והפקת מסמכים. כל המסכים בונים על אותם רכיבי UI בסיסיים (כפתור, שדה טופס, טבלה, תגית סטטוס).

**API (Node.js)  **נקודות קצה לפי תחום: positions, mapal, candidates, scoring, documents, auth, users. כל בקשה עוברת קודם דרך שכבת הרשאות.

**לוגיקה עסקית  **מנוע שקלול לפי קריטריונים ומשקלים דינמיים; מכונת מצבים שאוכפת את סדר 6 השלבים; מנוע תבניות למכתבים ודוחות.

**נתונים  **הישויות המרכזיות (פירוט בהמשך), ויומן סטטוס שמתעד את ההיסטוריה של המעברים בין שלבים.

**תשתית משותפת  **אימות, קבועים משותפים (ערכי החלטה, סולם השכלה), וה-starter kit.

**מודל הנתונים**

| ישות | מה היא מייצגת |
| --- | --- |
| USER | משתמש פנימי - מנהל מקצועי / רפרנט / חבר ועדה / מראיין / מנהל מערכת |
| AUTHORIZATION | תפקיד ההרשאה של המשתמש |
| POSITION | המשרה עצמה |
| MAPAL_CRITERION | תנאי סף או מדד הערכה במפ"ל של המשרה, עם משקל |
| COMPANY | חברת גיוס שמגישה מועמדים |
| CANDIDATE | האדם עצמו - שם ות"ז, לא משתמש במערכת |
| APPLICATION | הגשה ספציפית של מועמד למשרה, על ידי חברה |
| APPLICATION_SCORE | ציון של הגשה בקריטריון מסוים, בשלב מסוים |
| APPLICATION_DECISION | החלטה על הגשה - אחד משבעת הערכים הקבועים |
| DOCUMENT | מסמך שנוצר - מכתב תיחור או מכתב אישור סופי |
| STATUS_LOG | היסטוריית המעברים בין שלבים |


מועמד (CANDIDATE) נפרד מהגשה (APPLICATION) כי אותו אדם יכול תיאורטית להיות מוגש למספר משרות דרך חברות שונות. קריטריון מפ"ל הוא טבלה נפרדת מהמשרה, לא עמודות קבועות - כי לכל תפקיד קריטריונים ומשקלים שונים.

**הקשרים בין הישויות**

משתמש שייך לתפקיד הרשאה אחד, ויכול ליצור כמה משרות

משרה אחת מוגדרת לפי כמה קריטריוני מפ"ל, מייצרת כמה מסמכים, ועוברת בין שלבים

משרה מקבלת כמה הגשות, כל אחת דרך חברה מסוימת ועבור מועמד מסוים

הגשה אחת מקבלת כמה ציונים - אחד לכל קריטריון בכל שלב - ומקבלת החלטה אחת

רשימת ערכי ההחלטה וסולם ההשכלה הם lookup tables קבועים (seed data), לא טקסט חופשי - כדי שלא ייכתב "התקבל" פעם אחת ו"התקבלה" בפעם אחרת.

**בסיס הנתונים - SQL**

הנתונים קשורים זה בזה בצורה חזקה: למשרה יש כמה קריטריוני מפ"ל, לכל קריטריון ציונים של כמה הגשות, ולכל הגשה החלטה אחת. מסד יחסי עם foreign keys אוכף את זה אוטומטית - ב-NoSQL זה היה צריך להיאכף ידנית בקוד. לפרויקט בהיקף של 8 שבועות, SQLite מספיק (קובץ יחיד, בלי שרת נפרד), ועם Prisma כ-ORM המעבר בהמשך ל-PostgreSQL הוא שינוי קונפיג ולא שינוי קוד.

**טכנולוגיות וכלים**

**צד לקוח: **React + TypeScript, עם React Router לניווט ו-React Query לניהול קריאות API

**צד שרת: **Node.js + Express, גם ב-TypeScript

**ORM: **Prisma - מייצר טיפוסים אוטומטית מהסכמה, תומך גם ב-SQLite וגם ב-PostgreSQL

**מסד נתונים: **SQLite לפיתוח ולהדגמה

**אימות: **JWT - טוקן שנשלח בכל בקשה ומזהה משתמש ותפקיד

**גרסאות: **Git

**תקשורת ו-API**

REST, JSON בשני הכיוונים. הצד הקדמי קורא לשרת עם fetch/axios; השרת מדבר עם ה-DB דרך Prisma. אין צורך בשירותים חיצוניים אמיתיים בשלב הזה. כל בקשה עוברת קודם דרך middleware של הרשאות שבודק טוקן ותפקיד, לפני שהיא מגיעה ללוגיקה העסקית.

| שיטה | נתיב | מטרה |
| --- | --- | --- |
| POST | /api/positions | יצירת משרה חדשה |
| GET | /api/positions/:id | פרטי משרה |
| PUT | /api/positions/:id/mapal | הגדרת קריטריונים ומשקלים |
| GET | /api/positions/:id/status | סטטוס נוכחי + היסטוריית שלבים |
| GET | /api/positions/:id/applications | רשימת הגשות למשרה |
| POST | /api/applications/:id/scores | קליטת ציון להגשה |


GET /api/positions/:id הוא בעצם החוזה המרכזי בין חלקי המערכת - מסכי המסמכים והניקוד תלויים בנתונים שהוא מחזיר, אז השדות המדויקים שלו צריכים להיות מוסכמים מראש.

**זרימת הארכיטקטורה**

הבקשה עוברת בשרשרת קבועה מהצד הקדמי ועד מסד הנתונים:

React (Client)  ->  Auth Middleware  ->  Service Layer  ->  Database  ->


ציונים שנקלטים בשירות המועמדים משפיעים על הסטטוס בשירות המשרה

נתוני המשרה נדרשים לשירות המסמכים לצורך יצירת מכתבים

התלויות האלה הן החלק החשוב - הן מסמנות איפה חייב להיות חוזה API מוסכם מראש בין חלקי המערכת, ולא משהו שמתגלה רק באינטגרציה.

**עקרונות מערכת**

כל פעולה נרשמת ביומן - מי עשה מה ומתי, לא רק המצב הנוכחי

הרשאות לפי תפקיד נאכפות בשרת, לא רק מוסתרות בתצוגה
